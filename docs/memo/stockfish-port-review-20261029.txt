読み方
各コミットに、移植可否、対応する将棋側実装、理由、依存条件と必要な検証を記した。
題名だけの「一次分類」は廃止。上流差分と対応実装・有効な#if経路を照合した判定。
「修正推奨」は将棋にも同じ不具合/可搬性の欠陥があるもの。commit全体のcherry-pickや
全関連機構の導入を勧める意味ではない。将棋用の最小差分にする。
「条件付き推奨」は対象platform/前提機構/保守方針が合えば採用価値があるもの。
「実験候補」は性能・棋力が変わる案で、移植すれば速い/強いとの確認ではない。
「見送り」は現在の構成では大きな再設計・新モデル・未確認の前提が必要なもの。
「適用不要」は対象がない、導入元を採っていない、revert済み、または別projectの運用。
「対応済み」は同種の機構が現行に存在し、二重に追加すべきでないもの。
コードはまだ修正していない。文書の判定は修正実行の許可ではない。

系列ごとの扱い
・MultiPV/忘れた詰み:
  3e3e976f → fcbd160d → 1cebdafc → 1eff8b03 → 74a0a737を最終仕様にまとめる。
  途中版だけではpreviousScore/previousPVの世代問題が残る。再現済みSA-04と
  まだ通常USIで再現していない残りのcorner caseを区別する。
・TT aging/penalize:
  94beadff / 319d61efはバグ修正ではなく探索実験。導入するならc67c1ec6と
  db11ca42の検査、0111d11eのatomic、最終条件も必要。6a477d56のassert削除だけで済ませない。
・TT atomicとSWAR:
  0111d11eは現行にあるC++データ競合への対応。718a001eの型修正も参照する。
  ff3a6c50の21bit化は別の性能/衝突実験。現行で照合key幅を決めるのは
  HASH_KEY_BITSではなくTT_CLUSTER_SIZE。3なら16bit、他の対応構成なら64bit。
  64bit照合keyを21bitへ狭めない。手番によるcluster選択とkey抽出も将棋の仕様を保つ。
・Linux共有メモリ:
  現行には旧shm_linux.hが存在し、Linuxで有効。前回の「Linux共有メモリ未導入」は訂正。
  6a50807eのTHP化はこの旧backendにも対象がある。採るなら05f48577もセット。
  fd3c762f以降の新memfd/socket backendは未導入で、そのSIGPIPE/FD所有権等の修正は
  新backend導入時に必要。現行の確定不具合と混同しない。
・大容量mmap:
  7ab49b9bはmalloc arena再利用による複数NUMAの性能問題への候補。
  導入するなら5cae0fabのMAP_FAILED検査と7c37212eのNULL検査を含める。
・NMP/seekMate:
  9d4090e8は9a8dd81dでrevert。採用しない。再導入356d7c5cはbeta条件を強めた別案。
  seekMateを実験するなら598ae2c4/a35e229e/513ce075だけで終えず、
  72d52bbe/2035ddedのMultiPV sentinel対策まで含めて将棋向けに設計する。
・新NNUE:
  SFNNv15〜v19、QAT、K32Q2/K32H3、int8 FTは指定モデルと非互換。
  重みの交換やコードの差替えだけでは動かない。学習器/exporterと新モデルが必要。

実験候補を後で選ぶ場合
小さい共通変更からなら、AVX512 MoveSorter（04ce2c04/32619a02）、TT先行prefetch
（6f97594e）、continuation correction prefetch（4150d22b）、MovePicker local累積
（8f6a95de）、capture_stage再計算削減（1bf75bb3）が検討しやすい。
いずれもこの監査ではNPS改善を計測していない。複数案を一度に入れず比較する。
将棋の大きなhistoryを共有するf9b002cfは、初期化50221673とlarge-page確保まで含める。

既試行案との重複
FT/NNZ融合はfff35786と同種の案を以前NNUE_FT_NNZで試し、32threadで改善を確認できず。
以前の平均は-0.73%でばらつきもあり、上流と完全に同一実装を検証したという意味ではない。
NNUE_FT_SPECIALIZED、multi_ply、act15等も既存比較と照合し、未試行の新案として数えない。
FT重みprefetchの既試行案と、今回挙げたTT/history prefetchは対象が異なる。

追加で確認した不具合
SA-17: spin入力が非数値/過大整数だと未処理stoll例外でSIGABRT。
  通常releaseに setoption name Threads value abc を送るとinvalid_argument。
  999999999999999999999999999999ではout_of_range。評価関数ロード前の入力処理で起きる。
  cd75d311の入力検査部分が対応。spin値の将棋独自int64範囲を維持する。
SA-18: speedtestの秒→msでsigned int overflow。
  実Benchmark::setup_benchmarkへ "1 1 2147484" を渡すと、benchmark.cpp:198で
  「2147484 * 1000 cannot be represented in type 'int'」をUBSanが検出。
  正常入力 "1 1 1" は正常な4局面のgo movetime列を生成した。
  30290aa0を前回「対象外」とした判定は訂正。現行にもspeedtestが存在する。
  threads/ttSizeは将棋ではsize_tへ拡張済みで、上流と違い128*threadsのint overflowは
  今回再現していない。残ったint desiredTimeSの乗算と入力範囲を修正対象とする。

根拠と検証の限界
・前回の指定モデルでのASan/UBSan探索236ケース、追加4ケース、bench、perft6局面、
  accumulator 23,442手、部分キー48,322手の結果は既存台帳を参照。

  ではない。本体変更は禁じられているため行っていない。
・TSanは最小プログラムでも起動不可。Windows/Mac/BSD/LoongArch/RVV/複数物理NUMAの
  実機検証や長期棋力試験は未実施。条件付き判定にその前提を記した。
・標準unittestがSA-09/10で失敗する状態は変わっていない。
・証拠と作業用全patchはGit管理外build/search-audit-20261029/に保存。
