1. 優先度高: 1手詰めのTT保存時に詰み距離を正規化していない【再現済み】
場所:
  source/engine/yaneuraou-engine/yaneuraou-search.cpp:2918-2924 (通常探索)
  source/engine/yaneuraou-engine/yaneuraou-search.cpp:4769-4778 (静止探索)
  同:5217 value_to_tt、同:5233以降 value_from_tt

両経路で bestValue=mate_in(ss->ply+1) をそのままTTへ保存する。
一方、TTから読む際はvalue_from_ttで現在のplyを引くため、同じ局面・同じplyへの
再訪問でも詰みまでの距離が変わる。通常探索内の「変換してはならない」コメントも
TTの実際の保存規約と一致しない。

実際の関数呼び出しで確認した値:
  局面: 7nk/8l/7R1/9/9/9/9/9/K8 b R2B4G4S3N3L18P 1
  mate_1plyの返す手: B*2b
  ss->ply=4、1手詰めなので返値はmate_in(5)=31995。
  保存されたTT値=31995、正しくは局面からの距離でmate_in(1)=31999。
  2回目の呼び出しの返値=31991、正しくは1回目と同じ31995。
  通常探索・静止探索の両方で同じ誤差を再現した。

影響: 詰み距離、詰みスコアの大小比較、詰み距離枝刈りで誤った情報を使いうる。
今回、特定の実戦局面での最善手変更や棋力差までは検証していない。
修正方向: 保存値をvalue_to_tt(bestValue,ss->ply)で正規化する等。
証拠: mate_tt_probe.cpp / mate-tt-probe.log。通常USIだけの再現ではなく関数単位の再現。
Stockfish半年の同名修正ではなく、将棋独自の1手詰め経路の不具合。
補足: 全ての手が次の1手詰めを許す局面を通常USIで4回繰り返したテストでは、
最終表示は毎回score mate -2で正しかった（mate-usi-probe.json）。
したがって「通常USIの最終表示が必ず誤る」ではなく、保存値と再取得値の不整合を
関数単位で再現した指摘である。

2. searchmovesで指定した合法な不成が無視される【通常ビルドで再現済み】
場所: source/thread.cpp:439-466

GenerateAllLegalMoves=falseでは、指定手を選択的なMoveList<LEGAL>と照合する。
合法でも通常の生成で省略される不成が全て除外されると、rootMoves.empty()を
「制限なし」とみなすフォールバックで全候補手が再登録される。

再現（指定モデル・FV_SCALE=24・BookFile=no_book）:
  setoption name GenerateAllLegalMoves value false
  position startpos moves 7g7f 3c3d
  go depth 3 searchmoves 8h2b
  → bestmove 2g2f （指定集合外）
同じ入力でGenerateAllLegalMoves=true:
  → bestmove 8h2b （指定どおり）

cshogiでも8h2bが合法であることを確認した。
修正方向: 明示的なsearchmovesは全合法手として検証し、rootのMovePicker側にも
その候補が生成されるよう反映する。setup_rootMovesのフィルタだけ変えても十分とは限らない。
当面の回避策はGenerateAllLegalMoves=true。
証拠: searchmoves-probe.json / searchmoves-release-probe.log / searchmoves_probe.py。
将棋の選択的な不成省略に起因する独自問題。

3. 浅い探索終了時にponder抽出がMove::noneを擬似合法性判定へ渡す【通常USIで再現済み】
場所:
  source/engine/yaneuraou-engine/yaneuraou-search.cpp:5894-5901
  source/position.cpp:1386以降、特に1442
  source/types.h:765

置換表にhitしても、手がMove::noneの静的評価・静止探索エントリーがありうる。
extract_ponder_from_ttはm.is_ok()を確認せずpseudo_legal_s<true>(m)を呼ぶ。
pseudo_legal_s側も入口で特殊手を弾かず、from_sq()のASSERT_LV3で停止する。
pseudo_legalのコメントにある「特殊手ならfalseを返す」契約も満たしていない。

再現:
  新規起動、指定モデル・Hash64・定跡無効、isready後に
  position startpos
  go depth 1
  → ASSERT(is_ok()) / Move::from_sq → pseudo_legal_s → extract_ponder_from_tt。
  bench 64 1 1 default depth でも同じ停止を再現した。

これはASSERT_LV=3ビルドでの停止を確認したもので、既定のassert無効ビルドが
この入力でクラッシュするとは主張しない。
修正方向: ponder抽出で特殊手を弾く。pseudo_legal自体の特殊手に対する契約も確認する。
証拠: fresh-startpos-depth1.log / fresh-depth1.log / fresh_depth1_probe.py。

4. MultiPVの境界付きスコアが確定値として表示される【関数プローブで再現済み】
場所:
  source/engine/yaneuraou-engine/yaneuraou-search.cpp:5747-5751、5850
原因: isExact = i != pvIdx || !updated として、探索対象のPV以外のboundフラグを落とす。

状態を構成して実際のSearchManager::pvを呼んだ結果:
  MultiPV=2、pvIdx=1、rootMoves[0].scoreLowerbound=true
  → multipv=1のInfoFull.boundが空文字列。
  rootMoves[1].scoreUpperbound=true
  → multipv=2のInfoFull.boundはupperbound。
したがって前者だけが不正に確定値扱いになる。

影響: 解析・GUI・教師データ収集が、上界/下界を確定値と誤認しうる。
修正方向: 「更新済みか」と実際のboundフラグで表示を決める。
関連する中断時の詰みスコア/PVロールバックもまとめて確認する必要がある。
証拠: pv_boundary_probe.cpp / pv-boundary-probe.logのPROBE行。
同プローブ末尾には通常のdepth1探索もあり、項目3のassertも起きる。
対応するStockfish修正:
  3e3e976fdf54adf6fce636ff21f7c0f4ce66a70a (2026-05-04)
  https://github.com/official-stockfish/Stockfish/commit/3e3e976fdf54adf6fce636ff21f7c0f4ce66a70a
  [bugfix] Respect bound flags for searched moves in multiPV analysis

5. root moveのeffortで最初の1ノードを数え落とす【静的確認】
場所: source/engine/yaneuraou-engine/yaneuraou-search.cpp:3869-3874、4103、1970
Worker::do_moveはnodesを1増やすが、その後にnodeCountを保存している。
rm.effort += nodes-nodeCount はrootのdo_moveを1回分ずつ除外する。
通常のnodes統計自体は正しい。誤るのは各root moveのeffortと、それを使う時間配分。
修正方向: nodeCountの採取をdo_moveの前へ移す。
対応するStockfish修正:
  944bee71177601649150f44f4d2eee91418594ff (2026-05-10)
  https://github.com/official-stockfish/Stockfish/commit/944bee71177601649150f44f4d2eee91418594ff

6. LMRの負の削減が深い階層まで延長として連鎖する対策が未反映【要追加再現】
場所: source/engine/yaneuraou-engine/yaneuraou-search.cpp:3978
現状:
  max(1, min(newDepth-r/1024,newDepth+2)) + PvNode
StockfishはrootDepthの2倍以上深い階層では追加延長を抑制する修正を入れている。
やねうら王にはその条件がない。MAX_PLYの停止はあるため、無限再帰だとは主張しない。
探索量の膨張・応答遅延の候補だが、今回の将棋テストで同じ探索爆発は再現できていない。
将棋固有の延長調整もあるため、修正の移植前には局面・探索量・棋力の検証が必要。
対応するStockfish修正:

  https://github.com/official-stockfish/Stockfish/commit/1548538edecc4bd8aae119050c5f853935d25173
  Fix deep recursion.

7. null moveでcapturedPieceが残る【状態の不整合を再現、現行探索への実害未確認】

8. pthread版NativeThreadが生成失敗を無視する【失敗注入で確認、プラットフォーム限定】
